# 긴 문자(LMS/MMS) 주문 수집 — 설계

작성일: 2026-07-22
대상: ggotAIhp (주문폰 앱)
관련: `2026-07-21` 카톡·문자 주문 수집(`개발진행/카톡문자주문_설계.md`)

## 문제

한국에서 문자가 70자를 넘으면 SMS 가 아니라 LMS(장문메시지)로 전환되고, LMS 는
MMS 로 전달된다. 앱은 `SMS_RECEIVED` 만 듣고 있어(`AndroidManifest.xml`) 긴 문자가
**앱에 아예 들어오지 않는다.**

2026-07-22 실기기 확인:

| 시각 | 형태 | 결과 |
|---|---|---|
| 10:50:59 | SMS (62자) | 수집됨 |
| 11:13:52 | MMS | 유실 |
| 11:16:32 | MMS | 유실 |

```
11:16:30  Intent mimeType: application/vnd.wap.mms-message
          act=android.provider.Telephony.WAP_PUSH_RECEIVED
```

`SmsReceiver` 로그는 한 줄도 남지 않았다 — 실행조차 되지 않았다.

**조용히 유실된다는 점이 핵심이다.** 로그가 없어 사장님도 개발자도 알 방법이 없었다.
그리고 주소·받는분·날짜·연락처를 다 적은 **제대로 된 주문일수록** 70자를 넘겨 놓친다.

인계메모의 "70자 초과 문자 멀티파트 합치기 미검증"은 전제가 틀렸다. 한국 통신사는
긴 문자를 GSM 방식으로 쪼개 보내지 않고 LMS 로 바꾼다. `SmsReceiver` 의
`messages.joinToString("")` 는 국내에서 거의 타지 않는 경로다.

## 해결 가능성

MMS PDU 를 직접 파싱할 필요는 없다. 시스템이 저장한 것을 읽으면 된다.

```
content://mms/part → ct=text/plain
text=사장님 안녕하세요 내일 오후 3시까지 근조화환 하나 10만원짜리로 부탁드립니다. …
```

`READ_SMS` 권한이 이미 있어 접근 가능하다.

## 결정 사항

| 항목 | 결정 | 이유 |
|---|---|---|
| 놓친 것 따라잡기 | 한다 | 앱 재설치·재부팅 공백에 온 주문을 건진다 |
| 따라잡기 상한 | **6시간** | 사장님이 모르는 사이 오래된 주문이 자동 등록되는 것이 더 위험 |
| 첫 설치 | **0건** | 워터마크를 "지금"으로 세워 과거 메시지를 건드리지 않는다 |
| 사진만 온 메시지 | **주문 대화 중일 때만** "사진을 보냈습니다" 한 줄 | 손님이 사진으로 주문 붙이는 경우의 단서를 남긴다 |
| 트리거 | **MMS 도착 방송 + 앱 시작 시 1회** | 주기 작업(15분)은 최대 18분 지연이라 채널 간 속도가 어긋난다 |

### 트리거를 하나로 둔 이유

주기 작업을 안전망으로 겹치는 안(접근법 3)도 검토했다. 그러나 지금까지 잡은 결함이
대부분 **트리거가 여럿이라 서로 안 맞는 자리**에서 나왔다(`rpa_status='ready'` 를
아무도 집어가지 않던 문제가 같은 계열). 트리거를 둘로 늘리는 것은 문제가 실제로
관측된 뒤에 한다. 접근법 1의 약점(폰이 꺼진 동안)은 6시간 따라잡기가 덮는다.

## 구조

### 신규

| 파일 | 역할 |
|---|---|
| `receiver/MmsReceiver.kt` | MMS 도착 방송 수신 → 스캔 예약. **판단하지 않는다** |
| `mms/MmsScanner.kt` | 워터마크 이후 MMS 를 훑어 버퍼에 담는다 |
| `mms/MmsScanWindow.kt` | 조회 범위 계산(순수 함수) |
| `util/PhoneNumberNormalizer.kt` | 발신번호 정규화(순수 함수) |

### 수정

- `AndroidManifest.xml` — `RECEIVE_MMS` 권한 + 리시버 등록
- `LoginActivity.kt` — 런타임 요청 목록에 `RECEIVE_MMS` 추가
- 앱 시작 지점 — 시작 시 스캔 1회 호출

### 흐름

```
MMS 도착 → MmsReceiver → 5초 뒤 MmsScanner
                            ↓
              content://mms 워터마크 이후 수신건(msg_box=1) 조회
                            ↓
              발신번호(addr type=137) + 본문(part ct=text/plain)
                            ↓
              ── 여기서부터 기존 문자와 완전히 동일 ──
              OrderTextFilter → message_buffer → 3분 디바운스 → upload-text
```

**버퍼에 담는 순간부터 새 코드가 없다.** 기존 채널이 쓰는 길에 입구만 하나 더 낸다.
오늘 고친 스티키 시간 창, 디바운스, 중복 방어가 그대로 적용된다.

`MmsReceiver` 가 아무 판단도 하지 않는 것은 의도다. 정책을 방송 안에 넣으면
에뮬레이터 없이 테스트할 수 없다 — `KakaoMessageListenerService` 가 판단을
`KakaoNotificationPolicy` 로 뺀 것과 같은 이유다.

## 워터마크

`SharedPreferences` 에 "어디까지 봤는지" 시각 하나를 둔다.

```
조회 시작 = max(워터마크, 지금 - 6시간)
조회 끝   = 지금
```

`max` 가 핵심이다. 6시간은 **조회 범위가 아니라 상한선**이다.

| 상황 | 실제 조회 범위 |
|---|---|
| 평상시(5분 전에 봄) | 5분치 |
| 앱 프로세스 종료 후 재시작(8분 공백) | 8분치 |
| 폰이 이틀 꺼져 있었음 | 6시간치 (그 이전은 포기) |
| 첫 설치(워터마크 없음) | **0건** — "지금"으로 초기화 |
| **APK 재설치** | **0건** — 아래 참조 |

첫 설치 처리를 명시한 이유: 워터마크가 없을 때 6시간을 훑으면 앱을 깐 순간
사장님 폰의 지난 6시간 메시지가 통째로 들어온다.

**⚠️ APK 재설치는 따라잡기가 안 된다.** 워터마크가 `SharedPreferences` 에 있어
재설치하면 함께 지워지고, 앱은 이를 첫 설치로 보아 0건으로 시작한다. 즉 이 기능이
덮는 공백은 **프로세스 종료·재부팅**이지 재설치가 아니다.

이것을 "고치려고" 첫 설치 조회창을 넓히면 안 된다 — 그건 위에 적은 사생활 원칙을
정면으로 어긴다(앱을 깐 순간 지난 6시간 메시지가 통째로 들어온다). 재설치 중
유실이 실제로 문제가 되면, 워터마크를 서버나 백업 제외 저장소로 옮기는 쪽을
검토할 것.

관련해서 `AndroidManifest.xml` 의 `allowBackup="true"` 때문에 클라우드·스마트스위치
복원으로 **오래된 워터마크가 되살아날** 수 있다. 그러면 "첫 설치는 0건" 불변식이
"복원된 과거 6시간까지 수집"으로 바뀐다. 가능성은 낮고 6시간 상한·주문 필터가
막아주지만, 백업에서 워터마크 키를 제외하는 편이 정확하다.

**워터마크 전진 규칙**

```
본문이 아직 안 내려온 메시지가 있으면 → 그 중 가장 오래된 것의 수신시각 직전까지
전부 정상 처리됐으면                  → 조회 끝점(지금)까지
```

즉 **아직 읽을 수 없는 메시지는 넘어가지 않는다.** 그것만 남겨두고 그 앞은 전진한다.
다음 스캔에서 그 메시지부터 다시 본다.

업로드 성공 여부와는 무관하게 전진한다. 업로드 실패는 버퍼가 남아 재시도하는
구조라, 워터마크까지 붙잡으면 같은 메시지를 두 번 담게 된다.

**중복 방어 3겹**: 워터마크 / `countDuplicate`(발신자+본문+시각) / 서버 멱등성 인덱스.

## 추출 규칙

- **조회 대상**: 받은 메시지함(`msg_box=1`)만. 보낸 메시지는 보지 않는다.
- **본문**: `content://mms/part` 에서 `ct=text/plain` 인 파트만 모은다. 사진·동영상 파트는 버린다.
- **발신번호**: `content://mms/{id}/addr` 의 `type=137`(FROM).
- **고객명**: `ContactLookup` 으로 주소록 이름, 없으면 "신규"(통화·문자와 동일 관례).
- **필터**: 기존 `OrderTextFilter.shouldCollect()` 그대로.

### 번호 정규화

MMS 는 발신번호를 `+821049534339` 형태로 주는 경우가 있고 SMS 는 `01049534339` 로 준다.
같은 사람인데 **묶음 키(senderKey)가 갈라지면 스티키가 먹지 않고 주문이 두 건으로
쪼개진다.** `+82` → `0` 로 맞추는 정규화를 넣는다. 순수 함수로 분리해 테스트한다.

### 사진만 온 경우

```
글 파트 있음        → 글 수집
글 없고 사진만      → 주문 대화 진행 중이면 "사진을 보냈습니다." 한 줄
                     진행 중이 아니면 버림(앱 DB 에도 남지 않음)
```

"진행 중" 판정은 스티키 창(`MessageGroupDecider.STICKY_WINDOW_MILLIS`, 10분)을 쓴다.

## 실패 처리

**본문이 아직 안 내려온 경우** — MMS 는 도착 알림이 먼저 오고 본문이 뒤에 저장된다
(실측 1.5초, 통신 상태에 따라 더 걸릴 수 있음). 방송 후 **5초 뒤** 스캔하고, 그때도
글 파트가 비어 있으면 위의 워터마크 전진 규칙에 따라 **그 메시지 직전까지만**
전진시킨다. 다음 스캔에서 그 메시지부터 다시 보고, 6시간 안이면 복구된다.

이 규칙은 **머리 막힘(head-of-line blocking)**을 만든다. 어떤 메시지의 본문이 영영
안 내려오면(자동 다운로드 꺼짐) 워터마크가 거기서 멈춘다. 6시간 상한이 이것을
자동으로 푼다 — 조회 시작점이 `max(워터마크, 지금-6시간)` 이므로 6시간이 지나면
그 메시지를 지나쳐 진행한다. 즉 **막힌 메시지는 최대 6시간 뒤 포기된다.**

**자동 다운로드가 꺼진 기기** — 본문이 영영 내려오지 않는다. 앱이 해결할 수 없다
(사장님이 메시지앱에서 직접 받아야 한다). **한계로 기록**하고, 설정 화면 상태 표시는
실사용 후 판단한다(지금 넣으면 안 쓰는 기능이 될 수 있다).

**권한 없음** — 조회가 예외를 던진다. 조용히 삼키지 않고 로그를 남긴다. 카톡 알림
접근에서 얻은 교훈과 같다(꺼져 있으면 통째로 놓치는데 조용히 실패하면 알 수 없다).

## 테스트

프레임워크에 의존하지 않는 판단만 순수 함수로 분리해 단위테스트한다.

| 대상 | 내용 |
|---|---|
| `PhoneNumberNormalizer` | `+8210…` → `010…`, 이미 정규형, 하이픈 포함, 빈 값 |
| `MmsScanWindow` | 평상시 / 6시간 상한 / 첫 설치(0건) / 시계 역행 |
| 본문 조합 | 글 파트 여러 개 / 사진만 / 빈 파트 |

`ContentResolver` 를 타는 부분은 단위테스트가 불가능하므로 **실기기로 확인한다.**
이 영역은 단위테스트를 다 통과하고도 실기기에서만 결함이 드러난다는 것을
2026-07-21 에 이미 겪었다(스티키 유실, 가격 요구로 주문 폐기 등 4건).

### 실기기 검증 항목

1. 긴 문자(70자 초과) 1통 → 3분 뒤 서버 등록, 원문 안 잘림
2. 긴 문자 + 짧은 문자 연속 → 한 건으로 묶임
3. 사진만 1장(주문 대화 중) → "사진을 보냈습니다." 한 줄
4. 사진만 1장(주문 무관) → 서버에 안 올라감
5. 주소록 등록 번호 → 고객명이 이름으로
6. 앱 재설치 중에 온 긴 문자 → 시작 시 따라잡기로 복구
7. `RECEIVE_MMS` 자동 부여 여부 확인(`dumpsys package`)

## 권한

```xml
<uses-permission android:name="android.permission.RECEIVE_MMS" />
```

`RECEIVE_MMS` 는 SMS 권한 그룹이다. 앱은 이미 `RECEIVE_SMS`(런타임 요청) 와
`READ_SMS`(그룹 자동 부여) 를 보유하고 있어, 사용자 조작 없이 부여될 것으로 본다.
근거 — 현재 기기 상태에서 `READ_SMS` 는 요청한 적이 없는데 `granted=true` 이고
`USER_SET` 플래그가 없다(직접 허용한 `READ_CONTACTS` 에만 있다). 안전을 위해
`LoginActivity` 런타임 요청 목록에도 추가하고, 설치 후 실제 부여 여부를 확인한다.

향후 구글 플레이 배포 시 SMS/MMS 권한은 별도 신고가 필요하다. 현재는 APK 직접
설치 방식이라 해당 없다.

## 범위 밖

- 자동 다운로드 꺼진 기기용 안내 UI (실사용 후 판단)
- 주기 작업 안전망 (문제 관측 후 판단)
- 사진 내용 인식 (읽을 수 없다 — 한계)
- 기존에 유실된 긴 문자 소급 복구 (6시간 상한 밖)
